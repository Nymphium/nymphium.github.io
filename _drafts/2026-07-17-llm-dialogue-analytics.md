弊社では申請制でエンジニアは Claude Code が使えたりする。
日に 2、3 度の rate limit は当たり前、場合によっては月〜木で weekly limit にあたることも。
1 か月使いまくった結果 **264 セッション 3,487 の発話**があった。
1 つの発話を 1 ターンまたは T1（前述のとおり system 側のレスポンスが見えないのでユーザーの 1 発話と同じ）、以降 n ターンを Tn と書くことがある。
解析方法は Cursor (Composer 2.5) に `~/.claude/history.jsonl` を読ませ、有意なセッション・発話をピックしてもらい、さらにそれぞれの発話についても Cursor に分類（後述）させた。ただし、Cursor に任せたためか
Claude の system 側の発話は拾えなかった。
LLM に分類させたんで次に分類させなおすとおそらく異なる数字になるだろう。これはちゃあんと *真の機械学習* で分類させたほうがいいんですが、まあその程度の信憑性の記事です。
後述の通り貼り付けした数行のテキストも `[Pasted n text #1 +11 lines]` のようにマーカーだけ残り内容が読めないものもあった。
*not* 有意なものとしては、相槌やタスクの続行を促すもの（`ok`, `continue`）、git や作成した GitHub PRs の操作（`rebase master`, `create pr`）、agent commands（`/usage`、`/skills`）。
これらを捨てた結果、解析できそうな **238 セッション 2,932 発話**が残った。
| 段階 | セッション | 発話 | 備考 |
| --- | --- | --- | --- |
| 生データ | 264 | 3,487 | |
| 短文 552 件除外後 | 240 | 2,935 | 相づち・操作指示・agent command |
| agent command のみ除外後 | 238 | 2,932 | 分析の母数 |
除外した発話のうち、件数の多い代表パターン。
| 発話 | 回数 |
| --- | --- |
| continue | 66 |
| /usage | 50 |
| rebase master | 62 |
| ok / はい | 37 / 27 |
| PRコメント読んで修正 | 45 |
| create draft pr | 20 |
※除外パターンの内訳表は旧稿のまま。母数だけ Scrapbox 版に合わせた。
rate limit 気にしまくり奴。
類型のリファクタリング作業を並列でやらせているんで `create (draft) pr` / `rebase master` と `PRコメント読んで修正` が多い。PR コメントも一部 repository では Cursor
がレビューするようになっており、機械的に修正できる部分はこの程度の雑な指示でおこなわせている。有機的な存在からの一考の余地があるレビューは自分で考えたり Claude
と相談しつつ直すなどをおこなっている。`continue` は rate limit で止まったりうっかり escape などを押してしまったときに再開させている。
`ok/はい` は `続けますか?` とかいうマジで意味のない問いに答えている。これでトークン消費させるのは消費者をなめとるのか💢
これらの内容から、T1 と T2 以降、AI エージェントへの修正指示の 3 つに着目して分析をおこなわせた。
# T1
何事も始めが肝心。
T1 **238** 件の文字数中央値は **62** 文字（平均 **98.0** 文字）で、全発話 **2,932** 件の中央値 **32** 文字（平均 **49.1** 文字）のおよそ倍である。
T1 に文脈を載せ、T2 以降の発話は短く書く使い分けが出ている。
また、T1 は次の 4 つの分類に大別できる。
| 分類 | 指す内容 |
| --- | --- |
| 依頼 | 実装・修正・対応・起票など、エージェントに何かをしてほしい |
| 調査 | 調べて・集計して・原因を特定してほしい |
| 疑問 | 現状や方針について答えがほしい（実装依頼が主でない） |
| 背景説明 | 状況説明やログ貼り付けが中心で、依頼が弱いか無い |
依頼は例えば `eslint -> oxlint に置き換えてほしい` `<issue trackerのurl> これをやってください`
調査: `datadogを見て(自社アプリケーション)のn日間のメモリ使用量の遷移を調査` `モノレポ化可能かの調査 可能そうならやる 無理そうなら前段階の作業`
疑問: `このlockfileの更新ではどの画面をさわれば壊れてなさそう性がわかりますか?`
背景説明: `staging環境でのみError: Cannot find module 'react/jsx-runtime'…`
背景説明は概ね調査といったところだが、精度の低い調査依頼とも言えそう。
この分類で 238 セッションの T1 を分けると次のようになった。
| 分類 | 件数 |
| --- | --- |
| 依頼 | 169 (71.0%) |
| 調査 | 33 (13.9%) |
| 疑問 | 21 (8.8%) |
| 背景説明 | 15 (6.3%) |
さすがに依頼が多い。ワナビーなんで。仕事が山積みなわけだね。169 件の依頼からすると他の 3 つはわりとトントンとも見られる。背景説明は雑投げなんであんまりない。
## セッション長
セッションのターン数中央値は **6** ターン。
1 ターンで終わるのは **32** 件（**13.4%**）、7 ターン以上は **112** 件（**47.1%**）で、半分近くが長めのセッションである。
分類ごとにセッションの長さも違う。
| 分類 | セッション数 | 中央値 | 平均値 | p75 |
| --- | --- | --- | --- | --- |
| 依頼 | 169 | 5 | 12.4 | 12.0 |
| 調査 | 33 | 8 | 11.5 | 17.0 |
| 疑問 | 21 | 5 | 9.3 | 11.0 |
| 背景説明 | 15 | 9 | 16.8 | 31.0 |
疑問は短く、背景説明は長い。
疑問はすでにどうにかなっているものについてちょっと聞く程度なので疑問が疑問を呼ぶんでなければそう長くならない。
一方背景説明はとりあえずエラーログ貼っといたんでヨロシクって感じでほぼ調査なので問題解決しない場合（初見で分からずとりあえず投げる程度に複雑な問題なため）長引いてると推測できる。
# T2 以降
T2 以降があるセッションは **206** 件あった。
また 3 ターン以上続いたセッションでは、おおむね次の順序で発話が進む。
| ターン | 流れ |
| --- | --- |
| T1 | タスク内容の定義（URL とタスク） |
| T2 | 実装指示や質問・確認 |
| T3 以降 | 実装・質問・PR 作成・起票・ツール操作が交互 |
T2 以降の発話は旧 5 分類から再分割し、次の **9 分類**に分けた。
| 分類 | 指す内容 |
| --- | --- |
| 実装 | 新規のコード変更・機能追加・置き換えなど |
| 修正 | 既存コードや成果物の直し・指摘対応 |
| 質問 | 疑問形・理由や仕様の問い |
| 確認 | 現状確認・読んでほしい・大丈夫かの確認 |
| PR作成 | draft PR / create PR / commit&create PR など PR を新規作成 |
| 起票 | Linear / bd / Notion 等への issue・チケット作成 |
| ツール操作 | PR description 更新・レビュー対応・#番号参照・rebase・commit/push・CI・Slack など |
| 読めなかった貼り付け | 貼り付け本文がログに無く、文面から分類できなかった（多くは Pasted text マーカーのみ） |
| その他 | 完了報告・感想・方針の独り言・状況メモなど、上に当てはまらない発話 |
前述の通り、ctrl+v は `[Pasted text …]` みたいなマーカーになり内容が取得できないものがあった。
本文がログに載っていればその文面で分類する。マーカーだけで本文が無いものは「読めなかった貼り付け」とする。
旧「PR・起票」は PR作成 / 起票 / ツール操作 に分割した（PR 更新・レビュー等はツール操作）。

人間界では「まずは、ありがとうだよね」はコミュニケーションの常識だが、AI
コーディングエージェントとの会話となるとこちらの機微を相手に示したり丁寧な関係構築のメリットが薄い/ないので、こちらの機嫌の良さを一方的に押し付けたいとき以外はやる必要がない。
質問も、「これってほんとうに標準ライブラリにある関数でしたっけ(すっとぼけ)」のように当てつけのような質問をすることがあり（すまん、俺もくだらない人間なんや）、分類に悪影響を及ぼしている可能性が高い。のみなら
ずトークン効率も多分悪いんで、「こんな関数標準ライブラリにねえだろ、人間をイライラさせるな」くらい感情にも素直な指示を人間は出すべき。

# 理解や成果物の訂正
## 訂正の概要
T2 以降で、エージェントの理解や成果物を訂正する発話を数えた。訂正と判断できるものに限り、`ok` や `いや` だけの発話は除く。
訂正と判断した発話の例。

いや、.github/ を更新してほしいってだけね
いやサーバー動かしてwebwrightで触ってって意味だった
ローカルじゃなくて gh でたのむ
このコメいらんなあ / as importやめてや
逆に package ない場合自動で拾ってきちゃわないですか?

該当は **240** 発話で、238 セッションのうち **94** 件（**39.5%**）に分布する。
訂正が 1 回以上出た 94 セッションでは、1 セッションあたりの訂正回数は中央値 **2**、平均 **2.6**（最大 **17**）。
238 全体では中央値 **0**、平均 **1.0**。
訂正指示の発話の文字数は中央値 **36** 文字（平均 **57.1** 文字）。ヒスってお気持ち長文しているわけではないようだ。

## T1 と訂正
何事も始めが肝心。
T1 の文字数が、そのセッションの長さと、後から訂正の有無にどう影響するかを見る。
| 文字数帯 | セッション数 | 訂正あり（帯内 %） | 中央値 | 平均値 | p75 |
| --- | --- | --- | --- | --- | --- |
| 30 未満 | 41 | 17 (41.5%) | 8 | 18.7 | 17.0 |
| 30–59 | 76 | 28 (36.8%) | 6 | 11.3 | 13.0 |
| 60–119 | 53 | 26 (49.1%) | 6 | 12.5 | 12.0 |
| 120 以上 | 68 | 23 (33.8%) | 5 | 9.5 | 9.0 |
短い T1 ほどセッションは長くなりがち。120 文字以上は訂正率が下がる。
通説の通り、コンテキスト厚めに指示することで、軌道修正の必要をおさえられるようだ。
（ただし 60–119 帯だけ訂正率 49% と跳ねる。中途半端な長さがいちばん危ない、という読みもできる。）
T1 に URL があるかどうかで、その後の長さと訂正の出方が違う。
| URL | セッション数 | 中央値 | 訂正あり |
| --- | --- | --- | --- |
| あり | 66 | 4 | 23 (34.8%) |
| なし | 172 | 7 | 71 (41.3%) |
URL ありはセッションが短く、訂正も出にくい。
前述のとおり `<Linear issue URL>を読んで実装し、PRまで出して` という依頼がこれに該当し、ワンショットネスまでは見られなかったものの、事前に作成した issue
によりコンテキストを補強し、結果スムーズにタスクが推敲されていると読める。

## 占い：対話傾向
あなたは **「依頼で投げて、質問で操縦する」型**。
- T1 の **7 割が依頼**。仕事を「やって」と渡すのがデフォルト。疑問・背景説明は合わせて 15% 程度で、雑投げは少ない。
- なのに T2 以降の最多は **質問 42%**。手を動かす指示より「それ本当？」「こっちじゃない？」が多い。実装屋というより **編集長**。
- 訂正はセッションの **約 4 割**に出る。出たセッションは中央値 14 ターン、出ないセッションは 3 ターン。**訂正がセッション長を決めている**。
- 訂正の中身は成果物フィードバック 41% + 「いや別案」32%。意図そのものの訂正は 12% なので、**最初の意図はだいたい当たっていて、細部で揉める**タイプ。
- URL 付き T1 は中央値 4 ターン・訂正率低め。**Issue を先に書いてから投げる自分**がいちばん強い。
- 除外枠に `continue` / `rebase` / `create draft pr` が山盛り → rate limit と並列 PR 運用が生活習慣。対話の中身以前に **運用マシン**でもある。
一言で言うと、**仕事は依頼で始めて、会話は質問で伸ばし、訂正で長くする人**。財布に優しくしたいなら T1 を 120 字以上 + URL、訂正が出る前に終わる設計を。
